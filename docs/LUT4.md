# Frozen lookup4 matrix products

The provider recognizes standard ONNX graphs that decode packed 4-bit weights
through a 16-entry FP32 lookup table, multiply by block scales, reshape the
matrix and apply `MatMul`. This covers NF4 projections generated by onnax.
The same recognition handles a transposed weight for input-adjoint products.

For row-major weight shape `[K, N]`, byte `packed[i // 2]` contains the high
nibble for even `i` and the low nibble for odd `i`. With even block size `B`,

```
W[i] = table[code(i)] * scales[i // B]
Y = X @ W
```

The buffers have `ceil(K*N/B)*B/2` bytes and `ceil(K*N/B)` scales. Packed bytes,
scales and the lookup table are immutable initializer data. Computation,
scales, lookup values and outputs use FP32. The input may have dynamic leading
dimensions, including a vector or an empty batch.

## Execution

Recognition proves the Cast/Div/Mod, nibble concatenation, lookup, scaling,
trimming and reshape chain. Proven convex regions keep the decoder with its
matrix product during partitioning. The private execution plan then reads the
packed bytes and scales directly, and removes decoder nodes whose outputs have
no remaining consumers. Graph outputs, control-flow captures and shared
consumers retain their decoded values.

The Metal kernel decodes 16-by-16 tiles into threadgroup memory and uses FP32
SIMD-group matrix operations with compensated accumulation across K tiles.
A CPU stream uses a cached FP32 decode and ordinary CPU matrix multiplication.
Cache keys distinguish branch-local initializer storage and lookup values.
The exported ONNX graph and public operator registry keep their existing form.

Set `ONNXRUNTIME_EP_MLX_NO_LUT4_FUSION=1` to compare the original execution path.

## Reproduce the projection measurements

```bash
python tools/benchmark_lut4.py \
  --library /path/to/libonnxruntime_mlx_ep.dylib \
  --output lookup4.json
```

The tool compares original lookup4, fused lookup4 and cached FP32 models using
identical decoded weight values. Defaults are 64 rows, Qwen-sized 1024x2048 and
3072x1024 matrices, both weight orientations, 10 warmups and 100 measured calls.
Use `--shape 19x23 --rows 3 --warmup 0 --samples 1` for a short smoke run.

Each variant runs in a fresh process with ORT graph optimization disabled and
one runtime thread. Synchronous calls include CPU input/output exchange.
Peak RSS includes imports, session creation and execution. Metal allocation
samples come from a separate traced process; execution timing uses tracing
disabled. All three paths compare against independent NumPy arithmetic at
`rtol=1e-4, atol=1e-6`. The JSON records construction, median/P95, model sizes,
RSS, sampled `MTLDevice.currentAllocatedSize`, dispatch evidence, library hash,
hardware and software versions.

The checked-in [M1 Max FP32 report](benchmarks/lut4-m1max-fp32.json) contains the
complete measurements. Cached FP32 gives the GEMM control; lookup4 keeps the
weights packed throughout matrix execution.

## Validation

`tests/ops/test_lut4_fusion.py` covers dynamic shapes, both orientations, tail
blocks, nonlinear codebooks, shared outputs, branch-local weights, nonfinite
inputs and live parameter overrides. A three-projection chain verifies that
all products dispatch through the packed kernel, and the disable switch
provides the original-path control. Rust tests exercise CPU-stream cache
separation and region convexity, cache boundaries and quotient cycles.
